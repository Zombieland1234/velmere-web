## Architecture truth

The VLM checkout route currently uses:

- Stripe Checkout,
- `mode: "payment"`,
- server-authored product/price/currency,
- server-authored account/context/product-cell metadata,
- server-side idempotency,
- success URL as context only,
- webhook/server verification as the trust source for paid access.

There is no current `mode: "subscription"` VLM path and the webhook event allowlist does not implement `customer.subscription.*` or `invoice.*`.

Therefore renewal, subscription cancel and subscription downgrade are not silently scored as failures of a hidden product; they are **N/A / BLOCKED BY CURRENT ARCHITECTURE**.

Paid VLM checkout is additionally intentionally contained by:

`durable_opaque_server_checkout_flow_not_implemented`

and current commercial-tier policy fails closed for products that are invitation-only/not for public sale.

## Confirmed fixes

### 1. Durable readiness false positive

Before C14-P19, reconciliation readiness effectively treated:

`durableReady = serviceRoleConfigured`

as sufficient.

That is incorrect: this C14-P19 run proves the connected Supabase can exist while the required payment RPCs are absent.

The code now requires both:

- Supabase service-role configuration, and
- an explicit `VELMERE_STRIPE_DURABLE_STORAGE_QUALIFIED=true` qualification marker.

Without prior durable qualification it reports:

`stripe_durable_storage_not_qualified`

and remains fail-closed.

The marker must **not** be set merely to make readiness green. It is only appropriate after the target DB schema and lifecycle are actually exercised.

### 4. CI qualification

## Trust-source conclusion

- environment mode,
- product,
- product cell,
- amount,
- currency,
- account hash,
- context hash,
- session,
- PaymentIntent,
- payment status.
