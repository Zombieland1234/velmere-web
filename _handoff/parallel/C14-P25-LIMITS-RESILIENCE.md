## Changes

### 1. One server-time Redis fixed-window primitive

Added `lib/security/redis-fixed-window.ts` and made both Redis adapters use it.

The Lua script:

- reads `redis.call('TIME')` inside Redis,
- derives the fixed-window id and reset from Redis server time,
- validates persisted `window/count` state,
- increments and persists atomically,
- applies expiry atomically,
- stores only an opaque SHA-256-derived key.

The native Redis adapter and Upstash REST adapter now share the same window semantics and validation.

### 2. Closed an Upstash multi-instance clock-skew bypass

Before C14-P25, native Redis used Redis server time, while the Upstash REST path selected its bucket with application `Date.now()`. Two application instances on opposite sides of a reset boundary could therefore select different buckets for the same logical quota.

C14-P25 removes application-clock bucket selection from the Upstash path. The Redis server owns the window id and reset boundary.

Readiness now reports:

`upstash_rest_eval_server_time_fixed_window`

instead of the older local-bucket `INCRBY/PEXPIRE` adapter description.

### 3. Durable computations now fail closed instead of executing duplicates directly

A confirmed bypass existed in `lib/jobs/durable-computation-replay.ts`.

Previously these claim states could fall through to direct execution outside the durable store:

- `store_required`
- `store_failed`
- `in_progress`
- `retry_wait`
- `dead_letter`
- `conflict`

That could bypass idempotency, retry backoff, dead-letter state and duplicate suppression.

C14-P25 changes the behavior to:

- only explicit `direct` mode executes non-durably,
- `store_required` / `store_failed` fail closed,
- `in_progress` returns a retryable durable error,
- `retry_wait` preserves backoff,
- `dead_letter` stays dead-lettered,
- `conflict` stays conflicted,
- only a valid claimed owner executes and commits.

### 4. Worker heartbeat thundering herd removed

The worker heartbeat timer previously allowed a new async heartbeat call to start while the preceding call was still in flight. A slow store/network could therefore create overlapping heartbeat calls.

C14-P25 adds a single-flight heartbeat guard and exposes `heartbeatSkippedInFlight` in the drain summary.

A synthetic slow-heartbeat test proves maximum concurrent heartbeat calls remain 1.

### 5. Provider outage fan-out bounded

The Upstash REST failure domain now has a per-circuit in-flight request cap of **32**, in addition to the existing cooldown/recovery-probe behavior.

Native Redis already had an in-flight cap; the new private blackhole test verifies that 80 simultaneous calls remain fail-closed and accepted TCP connections stay at or below 32.

Readiness exposes:

- `providerRequestsInFlight`
- `providerInFlightLimit`

### 6. Invalid selected Redis configuration reports the correct provider

When native Redis was selected but invalid, the unavailable decision could still be described as an Upstash configuration failure.

C14-P25 reports:

- provider: `redis`
- providerError: `redis_configuration_invalid`

without attempting access to a disallowed remote plaintext Redis URL.
